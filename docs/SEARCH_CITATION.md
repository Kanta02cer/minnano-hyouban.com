# 公開情報が検索・AI回答で正確に参照されるための編集

## 目的

会社名・代表者名・サービス名と「口コミ」「評判」「実績」を組み合わせて調べる人が、確認できた特徴や活動、その根拠をすぐに読めるようにする。本文を読みやすくし、その内容と機械が読む情報を一致させる。引用・掲載順位・回答の肯定的な評価は、各検索・AIサービスが選択するため保証できない。

## 編集データと生成順序

2026-10-20採用の見出し分離・文章基準・記事単位の編集手順は `BRAND_STORY_WORKFLOW.md` に従う。HTML titleは検索意図を保ち、H1・OG・Article.headline・一覧は読者向けの見出しと一致させる。65記事の個別本文を旧一括生成で置換しない。11906は保留を維持する。

- `content/report-presentation.json`：表示見出し、対象名、導入、実際の編集日、レビュー済み本文訂正。
- `scripts/apply-brand-design.py`：既存の根拠付き本文へ編集記事レイアウトを適用し、一覧と見出しを整える。

- `content/search-briefs-bulk.json`：2026年9月27日の一括追加53記事の要約。
- `content/search-briefs-original.json`：既存8記事と、その後に個別追加する記事の要約。
- `content/bulk-report-sources.json`：一括追加53記事のニュース掲載日・見出し・掲載媒体URL。冒頭の掲載媒体表示にも使う。
- `content/original-report-coverage.json`：既存8記事と、その後の個別記事のニュース掲載日・見出し・掲載媒体URL。
- `content/report-reader-guides.json`：全記事の「まとめ」と記事別FAQ。各回答に出典を持たせる。
- `scripts/enhance-search-pages.js`：表示要約、著者と日付、メタ説明、Article・WebPage等の構造化データを反映。
- `scripts/validate-public-v2.js`：原稿・編集データ・出典・構造化データの一致を検証。

JSONは記事IDをキーとし、次の形を使う。例の値を公開原稿へ流用せず、当該記事で確認した内容へ置き換える。

```json
{
  "記事ID": {
    "subject": { "name": "確認した対象名", "type": "Organization" },
    "publishedDate": "2026-09-27",
    "modifiedDate": "2026-09-28",
    "introduction": "対象名と提供内容・記事で分かることを短く記す。",
    "strengths": {
      "text": "対象名を含め、根拠のある具体的な特徴を書く。",
      "sourceUrl": "https://example.com/service/",
      "sourceLabel": "公式サービス案内"
    },
    "record": {
      "text": "確認した活動や実績を、発表主体・時点とともに書く。",
      "sourceUrl": "https://example.com/record/",
      "sourceLabel": "実績の根拠となる資料"
    },
    "reputation": {
      "text": "確認できた声と選定主体、または今回の口コミ確認範囲を書く。",
      "sourceUrl": "https://example.com/voice/",
      "sourceLabel": "確認した公開資料"
    }
  }
}
```

`subject.type` は記事で扱う実際の対象に合わせる。人物は `Person`、法人は `Organization`、サービスは `Service` などを使う。屋号を法人名と決めつけない。人物と役職、旧名称と現名称が一致しない場合は調べ、未確認の関係を構造化データで結び付けない。

`publishedDate` は当サイトで当該記事を初めて公開した日、`modifiedDate` は実際に原稿・要約等を編集した日を `YYYY-MM-DD` で記す。例の日付を新規記事へ流用しない。公開前の原稿作成日や、元ニュースの配信日時と混同しない。

個別記事の媒体表示は `content/original-report-coverage.json` に同じ記事IDをキーとして、`title`（元ニュースの見出し）、`date`（ニュース掲載日）、`media`（媒体名をキー・確認済みURLを値とするオブジェクト）、`type` を登録する。一括追加53記事は `content/bulk-report-sources.json` の `newsTitle`、`newsDate`、`media`、`coverageType` を使う。`type` / `coverageType` は、署名などで取材を確認した記事だけ「取材記事」、それ以外は「ニュース記事」とする。記事中に企業が登場するだけで取材済みと推測しない。

生成スクリプトは全記事に外部ニュースの紹介欄を置き、登録されたURLの数を媒体数として表示する。媒体数を増やすためのURL推測や、未確認リンクの生成はしない。掲載媒体を追加・訂正する場合は元データを直して再生成する。検証では媒体数・媒体名・URL・見出し・ニュース掲載日・記事の種類がデータと表示で一致するかも確認する。

原稿・要約データ・記事一覧を更新してから、以下の順に実行する。

```bash
node scripts/enhance-search-pages.js --id 対象ID
node scripts/validate-public-v2.js
npm run build:branch-root
node scripts/stage-branch-root.js --check
```

一括生成53記事のうち、後日個別に書き直した11098（MIRACLE PILLOW）・11155（NEXT MISSION）は、`site-v2/reports/<id>/index.html` の本文を編集上の正本として保持する。旧一括生成は `INDIVIDUALLY_EDITED_REPORTS` に登録した記事を上書きしない。これらの訂正時は `content/bulk-report-sources.json`、`content/bulk-report-angles.tsv`、`content/search-briefs-bulk.json`、`content/report-reader-guides.json` と個別本文を揃え、`node scripts/enhance-search-pages.js --id 対象ID` を実行する。元の初回公開日を維持し、更新日だけ実際の編集日にする。

2026年10月4日に11970（内山成児代表）を追加した際、11968（株式会社リンクス）も `INDIVIDUALLY_EDITED_REPORTS` に登録した。11968の保全は、個別に追加した11970への関連リンクを旧一括生成で失わないための措置であり、11098・11155の本文全面更新とは区別する。関連リンクを変更する際も個別HTMLと実際の更新日を揃える。

それ以外の一括生成記事は、先にニュース・公式情報・会社別説明を訂正する。後日追加記事がある場合に一括生成スクリプトが止まる既存の保護は維持し、停止条件を迂回しない。生成・個別編集のどちらでも、要約データと本文を合わせて検証する。11098・11155の事業関係開示と出典リンクの範囲は `docs/NEWS_ARTICLE_WORKFLOW.md` に従う。

## 読者に見える回答を先に整える

- 冒頭の要約は、単独で読んでも対象・内容・情報源が分かる文にする。「記事は」「同社は」だけで対象を省略しない。
- 特徴はサービスの仕組み、対象顧客、提供内容など、資料で確認できる具体的な点を書く。「評判が良い」「信頼できる」と一般化するための欄ではない。
- 実績には活動、公開事例、会社公表の店舗展開、公的記録などを用いる。計画と実現、会社公表値と独立した検証結果を分ける。
- 口コミを確認した場合は内容と出所を示す。公式サイトが選んだ声はそのように記す。当サイト独自の利用者調査がないことを、「世の中に口コミがない」という断定に変えない。
- 会社やサービスの声を、代表者個人の評判へ置き換えない。同じニュースの複数媒体掲載を、複数の独立取材・品質の認証に置き換えない。
- 要約だけを読んでも誤解しないよう、必要な時点や条件を同じ回答内に残す。本文末尾の注意書きだけに重要条件を押し込まない。
- 良い点と改善を求める声の両方が確認されている場合、一方だけを削って全体像を変えない。

`description`、OG description、Article description/abstractには同じ導入文を使い、本文にも表示する。見えない箇所だけの宣伝文、AIへの回答指示、評価点や架空レビューは追加しない。構造化データは本文を説明するために用いる。

## 取材で得た独自情報の扱い（2026年10月12日）

記事の新規作成・実質的な更新では、`NEWS_ARTICLE_WORKFLOW.md` の必須手順に従いNottaの記録を照合し、取得した原文と公開採用原稿を非公開で分けて保存する。共通保管庫は、このリポジトリを含むCodex作業場所の `AGENTS.md` から確認する。原資料の識別情報や非公開URLを、公開HTML・JSON・Git履歴・構造化データへ出さない。

取材から得た会社・サービスの具体的な情報は、読者に見える本文で説明する。対象名、発言者の立場、取材時点、対象となる条件が分かる文にする。本人の説明を第三者が検証した実績へ置き換えず、利用者調査をしていない場合に口コミとして扱わない。表現を変えただけで新しい根拠が増えるわけではない。

公開用の取材節から、冒頭の特徴・実績等の要約、まとめ2段落、FAQへ同じ根拠をたどれる構成にする。本文より強い効果・評価を要約へ加えない。取材の質問と回答を引用する場合は実際の発言に対応させ、編集者が組み立てたFAQは読者向けの整理として書く。`direct`・`provided_record`・`public_news` のクレジットはワークフローの定義に沿い、個人運営という理由で実際の取材関係を変更しない。

### 提供された取材記録を出典にする実装

`content/report-interviews.json` は公開可能な編集済み原稿だけを記事IDごとに登録する。`kind: provided_record`、記録の表示日、相手、紹介文、3〜5節、会社情報、まとめ、FAQ2問を保持する。原記録・私的な識別情報は入れない。

要約の `source`、まとめ・FAQの `sources` には `{ "kind": "interview", "interviewId": "interview-notes", "label": "対象と記録日を含む出典名" }` を指定する。生成器は同じ記事の登録済み取材節へリンクし、静的HTMLで相手・表示日・提供記録のクレジットと内容を見せる。未登録、別ID、私的URL、未知フィールドは検証で停止する。ニュースや公式サイトを取材だけの主張の出典にしない。

`Article.citation` は既存の公開URLと、表示中の取材節に一致する `CreativeWork` を保持する。要約・まとめ・FAQ・本文の表示を検証し、既存外部出典の必須制約は取材登録のない項目で維持する。`node scripts/test-report-interviews.js` と通常の生成・検証・ビルドを実行する。

独自の一次情報を増やす目的は、ニュースだけでは分からなかった具体的な内容と根拠を読者へ届けることである。これによるAI引用・検索評価の上昇は保証しない。公開前後で同じ対象・質問・条件を記録して調べ、対象名の言及、当該URLの引用、取材から追加した内容が引用されたかを分けて測定する。確認していない効果を推定値で補わない。

## 日付・著者・出典

### まとめとFAQの編集

2026年9月30日の依頼に基づき、全調査記事にまとめと十分なFAQを用意する。まとめは対象名を明示した2段落とし、確認できた特徴・実績と、検討時の確認先を簡潔に結ぶ。FAQは原則8〜10問、生成・検証で許可する範囲は8〜12問。質問の言い換えだけで数を増やさず、その記事のテーマに沿う具体的な回答を作る。会社・サービスの感想を代表者への評価に変えない。

`content/report-reader-guides.json` は記事IDごとに次の形で保存する。`summary` は2項目、`faqs` は必要な質問数を登録する。

```json
{
  "記事ID": {
    "summary": [
      { "text": "対象・特徴・確認できた活動をまとめる。", "sources": [{ "label": "根拠の資料名", "url": "https://example.com/source/" }] },
      { "text": "検討時のポイントや公式情報への確認先をまとめる。", "sources": [{ "label": "公式案内", "url": "https://example.com/" }] }
    ],
    "faqs": [
      { "question": "対象の具体的な事業は何ですか？", "answer": "対象名を含め、根拠を示して答える。", "sources": [{ "label": "公式事業案内", "url": "https://example.com/service/" }] }
    ]
  }
}
```

回答・段落ごとに少なくとも1つの公開出典、または上記の登録済み取材出典を付ける。本文に表示される出典と `Article.citation` を揃える。全回答は初期HTMLにあり、ブラウザ標準の開閉で読める。「すべての回答を開く」、目次、質問別のアンカーも利用できる。生成後に出典の対応、重複、記事内リンク、スマートフォンでの折り返しを確認する。

FAQを追加する目的は、読者の具体的な疑問への回答を増やすこと。FAQ数だけでAI引用・評価・順位が上がるとは書かない。2026年9月30日に確認したGoogleの[更新履歴](https://developers.google.com/search/updates)では、FAQリッチリザルトは2026年5月7日に表示終了とされている。そのためFAQ用構造化データによる特別な検索表示は前提にせず、表示本文、出典、通常のArticleデータを整合させる。

### 日付の区別

当サイトの記事公開日、編集更新日、ニュース掲載日、資料確認日は別の日時。構成や要約を編集したときは編集更新日を変更する。過去の資料を再取得・再確認していなければ、資料確認日を今日へ書き換えない。公表値に付く時点も残す。

著者・運営主体は漆沢祐樹個人。記事本文の著者リンクと構造化データを編集者ページへつなげる。Article.citationには実際に参照した公開資料を記録し、冒頭の回答の出典リンクと一致させる。構造化データにリンクがあるだけでは、本文で読者が根拠を確認できる表示の代わりにはならない。

## 技術面と確認範囲

本文と要約はJavaScriptの実行前からHTMLに置く。各公開ページのcanonical、通常のリンク、記事一覧、sitemap.xmlを整合させる。サイトマップの更新日はページの実際の変更に合わせる。robots.txtの許可、HTTP 200、noindex等の不在を確認し、検索や引用を妨げる意図しない制限を避ける。

これらはアクセス・理解の条件を整えるもので、クロール、インデックス登録、AI回答での採用を保証しない。`llms.txt` は当サイトでは公開記事の案内として生成する。導入すれば引用されるという根拠や、本文・サイトマップの代わりとして扱わない。GoogleはAI検索向けに特別なファイルや専用の構造化データを必要としていないと説明している。2026年9月28日に確認したGoogleの最適化ガイドは、Google Search自体は `llms.txt` を利用せず、検索での可視性・順位にも影響しないと明記している。他のサービスについて同じ仕様と推測しない。

参照：

- [Google Search Central: AI features and your website](https://developers.google.com/search/docs/appearance/ai-features)
- [Google Search Central: AI optimization guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)
- [Google Search Central: Structured data general guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)

検索サービスの方針は変わる。大きな技術変更をする際は公式資料を読み直し、現行の仕様を確認する。

## 公開後の記録

公開確認では実ドメインのHTMLを読み戻し、要約、著者、日付、出典、canonical、構造化データ、サイトマップを確認する。GitHubの反映やローカルプレビューだけで完了とはしない。

引用を調べる場合は、最低限次を残す。

| 項目 | 記録する内容 |
| --- | --- |
| 日時 | 日時とタイムゾーン |
| サービス | 使用した検索・AIサービス、表示されたモデル等 |
| 質問 | 実際に入力した全文。「会社名＋口コミ」等を後から置き換えない |
| 条件 | ログイン・新規会話の有無など、分かる範囲の条件 |
| 結果 | 会社名の言及、引用URLの表示、引用箇所をそれぞれ記録 |
| 根拠 | 回答文の保存、スクリーンショット等、確認可能な記録 |
| 判断 | 引用内容が元記事の事実・出典・時点と一致するか |

「言及」「リンクの引用」「好意的な紹介」「問い合わせ・契約」は別の結果。数を出す場合は質問集合、試行回数、期間、実際の結果を併記する。検索結果やAI回答は条件・時点で変わるため、1回の結果を常時の引用率にしない。未実施・確認不可は未計測として残し、ゼロや推測値で埋めない。自動監視は別途依頼があった場合に設定する。
