# ニュースから調査記事を追加する手順

この文書は、みんなの評判.com の記事を別の Codex タスク・アカウントからも同じ編集方針で更新するための作業手順です。現在の作業場所は `/Users/urushizawayuuki/Documents/Codex/2026-09-26/https-minnano-hyouban-com-https-minnano/work/minnano-hyouban.com`。場所が変わった場合は、このリポジトリの `AGENTS.md` と本書を探して読み直してください。チャットの履歴やログイン状態を唯一の記録にしません。

## 開始条件と入力

ユーザーがこのサイトのニュースの本文や URL を Codex に貼ったら、そのタスク内で調査・原稿作成・サイト更新を開始します。ユーザーが「下書きだけ」と指定しない限り、検証後に本番反映まで進めます。公開権限や資料が不足する場合は、完成した原稿と具体的な未完了箇所を渡します。Codex は貼付を監視する常駐処理ではありません。別タスクで始めるときは、**このリポジトリを作業対象として開き、ニュース URL・対象会社を一緒に貼る**と確実です。URL や会社名が欠けても、分かる範囲の調査から始めます。

初めに `git status --short`、現在のブランチとリモート、`site-v2/`、`scripts/build-public-v2.js`、公開サイトを確認します。前回のローカル差分・公開結果を推測しません。2026-10-12確認時点の実ドメインはXServerです。GitHub mainルートは履歴・ミラーであり、pushだけでは実ドメインは更新されません。`.github/workflows/deploy.yml` はビルド成果物と公開ルートの一致を検証します。ホスティングの実態は毎回確認します。資格情報をソースや文書に記録しません。

## 調査と原稿

1. 貼付されたニュースの掲載日時、対象人物・会社、原文 URL、同じ記事が載った各媒体 URL を確認する。見出しが似ているだけの別記事を同一扱いしない。同じ記事が4媒体に載った場合は「4媒体に掲載」と表現し、「4媒体が別々に取材」とは書かない。4媒体の主張は、当該記事について4 URL を確認できたときだけ使う。
2. 公式サイト、会社概要、サービス詳細、料金・利用条件、事例、プレスリリース、公的資料、公開された利用者の声を追加調査する。ニュース本文の言い換えだけで終えず、サービスの仕組みと対象読者に役立つ情報を独自に整理する。公式サイト・サービスページへの分かりやすい導線を置く。
3. 情報を「ニュースの記述」「会社・本人の公表」「公的・独立資料」「口コミ」「編集上の整理」に分ける。数値には発表主体と時点を添える。公式サイトの声は選定された声と分かるように書き、全体の評判や満足度へ一般化しない。直接取材や独立した口コミがなければ作らない。批判的情報も確認できたものは省略して誤認を招かない。
4. 会社や人物のブランディングに役立つ、読みやすく好意的な紹介にする。信用・実績として述べるのは掲載や公表によって確認できた範囲に限る。掲載料・制作費・取材協力・PR の有無や原稿執筆者との関係は記事ごとに確認して記載する。既存3社が無償だったことを新規企業へ流用しない。元記事の本文を長く転載せず、自分の言葉でまとめる。

### Nottaの取材記録を使う必須手順（2026年10月12日）

記事の新規作成・実質的な更新では、ニュース・公式情報の調査に加えて、毎回、対象企業・サービスに対応するNottaの取材記録を確認する。保存先と索引の正本は、このリポジトリを含むCodex作業場所の `AGENTS.md` が案内する非公開の共通保管庫とする。アカウントやチャットを切り替えても同じ保管庫から再開する。公開リポジトリには、生の記録名・記録ID・非公開URL・録音・全文文字起こし・個人連絡先・内部メモを記載しない。

1. **照合する。** 会社・サービス名、取材相手、取材日、ニュースのテーマを照らし合わせ、採用する記録を特定する。似た社名や同じ代表者という理由だけで別の取材を結び付けない。表題だけで判断せず、本文中の会社・商品名、事業内容、自己紹介・役職・話者の文脈をニュースと照合する。親子会社や同じ人の別事業を混同しない。結果は根拠時刻付きの `identityMatch` として非公開で残す。該当記録がない場合は公開資料による記事とし、取得できない場合は「記録なし」と扱わず、未確認として残す。
2. **取得した版を残す。** 取材記録を記事化に使う前に、取得日時・元資料との対応・利用可能な範囲を非公開保存する。保存済みの原本を編集・上書きせず、新しく取得した版や訂正版を別に残す。取得した原文、校正した文字起こし、公開用に編集した採用原稿、公開結果を区別する。同じ記録が改訂されている場合も、以前の版と採用根拠を失わない。
3. **発言を確かめる。** 話者、取材時点の役職、固有名詞、数値、年月、否定表現、提供済みと計画の区別を確認する。引用や重要な主張は音声を確認できる場合は該当箇所を聴き、文字起こしの誤認識を修正する。音声を確認できなかった箇所はその状態を記録し、不明な発言を推測で補わない。各採用箇所から原記録の行・時刻等へ戻れる対応を非公開で保持する。
4. **公開できる範囲を確かめる。** 既に示されている利用許諾やユーザー指示を確認し、取材者・取材目的・資料提供者と、公開可能な発言・氏名・事例を整理する。オフレコ、顧客の機密、未公表の数値、第三者の個人情報をそのまま採用しない。確認が必要な箇所は採用原稿から分け、既に解決した許諾を取り直さない。
5. **会社・サービスの独自情報に編集する。** サービスを作った背景、品質を守る基準、作業や導入の流れ、顧客への対応、具体的な事例と条件、提供できる範囲など、読者の判断に役立つ発言を選ぶ。本人・会社の説明と、外部資料で裏付けた事実、編集者の整理を分ける。ニュースの言い換えだけを「独自情報」と呼ばず、どの内容が取材資料から加わったかを確認する。
6. **本文と要約を合わせる。** 公開可能な取材の要点を本文に置き、冒頭要約・まとめ2段落・記事固有FAQ8〜10問へ接続する。取材で実際に聞いた質問と、編集者が読者向けに整理したFAQを区別する。聞いていない質問と回答を、逐語のインタビュー形式として作らない。各回答に取材時点・対象・条件を残す。非公開資料を出典にする技術上の制約は `SEARCH_CITATION.md` の手順に従う。

社長の人生・キャリア・価値観を中心とする話は姉妹メディアの論点と分け、当サイトでは会社・サービスを選ぶための具体的な情報に編集する。同じ取材資料を使っても同じ本文を複製せず、関連する公開記事がある場合に相互リンクする。

#### 取材の区分とクレジット

以下は編集上の区分。公開用の提供記録は `content/report-interviews.json` と `scripts/lib/report-interviews.js` で実装・検証する。実際の取材者・所属・提供経緯を確認して選ぶ。

| 区分 | 根拠と読者への表現 |
| --- | --- |
| `direct` | 当サイトの編集者が本人に直接話を聞いた事実がある場合。「○年○月、○○氏にオンラインで取材」など、日付・相手・方法・実際の取材者を示す。 |
| `provided_record` | 別の機会・名義の取材記録を提供され、当サイトで編集する場合。「提供された取材記録をもとに、サービスの特徴を再構成」などと記す。元の取材者・取材関係を確認し、当サイトによる新規の独自取材に置き換えない。 |
| `public_news` | 公開されたニュース・インタビュー記事のみを参照する場合。「掲載記事では○○氏は〜と説明」とし、確認した公開URLへつなぐ。記録を取得したことや本人と直接話したことを意味しない。 |

当サイトの個人運営・無償掲載と、実際の取材を行った仕事・所属・事業上の関係は別の情報である。例えば別事業で実施された取材記録を利用するときも、その事実を当サイト独自の取材と誤認させない。本文の既存の「直接取材は行っていません」は、対象記事について確認した区分に合わせて更新する。利用者調査・サービスの実地検証の有無は独立した項目であり、一緒に実施済みへ変更しない。まだ取材資料を反映していない他の記事の説明を一括で変更しない。

## ページ作成

- 新規記事・文章改稿は `BRAND_STORY_WORKFLOW.md` と `WRITER_READER_WORKFLOW.md` の共通プロンプトを使用する。ライター役の初稿を一般読者役が初見で確認し、指摘への修正後に再確認する。最低2回の読者確認を行い、具体的な未解決点があれば追加で往復する。本文だけでなく導入、段落の接続、まとめ、FAQも対象にし、最後に原資料との整合を確認する。推敲記録は公開リポジトリ外の親作業場所 `work/editorial-reviews/` に保存する。

## 検証、公開、記録

生成前に `docs/SEARCH_CITATION.md` の「公開中のAIパッチを保全する」を確認し、公開中の本文・構造化データと編集元の差分を解消する。取材原文を保存したこと、公開用の採用原稿ができたこと、出典型が実装されたこと、実際に公開・引用されたことを別々に記録する。

```bash
node scripts/enhance-search-pages.js
node scripts/validate-public-v2.js
npm run build:branch-root
node scripts/stage-branch-root.js --check
python3 -m http.server 8080 --directory dist
```

ビルド後、ローカルのトップ、一覧、新規記事、同社記事との相互リンク、公式サイト CTA、PC とスマートフォンの表示、アニメーションの負担と縮小設定を確認します。検証スクリプトは構造上の漏れを検出するもので、ニュースの真偽や口コミの代表性は人が資料で確認します。公開前に `git diff` と `dist/` の対象を見直します。
