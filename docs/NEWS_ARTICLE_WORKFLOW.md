# ニュースから調査記事を追加する手順

この文書は、みんなの評判.com の記事を別の Codex タスク・アカウントからも同じ編集方針で更新するための作業手順です。現在の作業場所は `/Users/urushizawayuuki/Documents/Codex/2026-09-26/https-minnano-hyouban-com-https-minnano/work/minnano-hyouban.com`。場所が変わった場合は、このリポジトリの `AGENTS.md` と本書を探して読み直してください。チャットの履歴やログイン状態を唯一の記録にしません。

## 開始条件と入力

ユーザーがこのサイトのニュースの本文や URL を Codex に貼ったら、そのタスク内で調査・原稿作成・サイト更新を開始します。ユーザーが「下書きだけ」と指定しない限り、検証後に本番反映まで進めます。公開権限や資料が不足する場合は、完成した原稿と具体的な未完了箇所を渡します。Codex は貼付を監視する常駐処理ではありません。別タスクで始めるときは、**このリポジトリを作業対象として開き、ニュース URL・対象会社を一緒に貼る**と確実です。URL や会社名が欠けても、分かる範囲の調査から始めます。

初めに `git status --short`、現在のブランチとリモート、`site-v2/`、`scripts/build-public-v2.js`、公開サイトを確認します。前回のローカル差分・公開結果を推測しません。公開経路は現時点で GitHub Pages の `main` ルート公開です。`.github/workflows/deploy.yml` はビルド成果物と公開ルートの一致を検証します。ホスティングの実態は毎回確認します。資格情報をソースや文書に記録しません。

## 調査と原稿

1. 貼付されたニュースの掲載日時、対象人物・会社、原文 URL、同じ記事が載った各媒体 URL を確認する。見出しが似ているだけの別記事を同一扱いしない。同じ記事が4媒体に載った場合は「4媒体に掲載」と表現し、「4媒体が別々に取材」とは書かない。4媒体の主張は、当該記事について4 URL を確認できたときだけ使う。
2. 公式サイト、会社概要、サービス詳細、料金・利用条件、事例、プレスリリース、公的資料、公開された利用者の声を追加調査する。ニュース本文の言い換えだけで終えず、サービスの仕組みと対象読者に役立つ情報を独自に整理する。公式サイト・サービスページへの分かりやすい導線を置く。
3. 情報を「ニュースの記述」「会社・本人の公表」「公的・独立資料」「口コミ」「編集上の整理」に分ける。数値には発表主体と時点を添える。公式サイトの声は選定された声と分かるように書き、全体の評判や満足度へ一般化しない。直接取材や独立した口コミがなければ作らない。批判的情報も確認できたものは省略して誤認を招かない。
4. 会社や人物のブランディングに役立つ、読みやすく好意的な紹介にする。信用・実績として述べるのは掲載や公表によって確認できた範囲に限る。掲載料・制作費・取材協力・PR の有無や原稿執筆者との関係は記事ごとに確認して記載する。既存3社が無償だったことを新規企業へ流用しない。元記事の本文を長く転載せず、自分の言葉でまとめる。

## ページ作成

- 代表者ニュースと会社・サービスニュースが**異なる話題**なら、`site-v2/reports/<slug>/index.html` を別々に作って相互リンクする。単なる同一記事の転載先は別ページにしない。既存 URL の記事を更新するときは URL を維持する。新規 slug はニュース固有の ID が使えるならそれを、なければ一意の英数字とハイフンで作る。
- 既存のレポートを雛形にし、概要、会社・サービス説明、ニュースから分かる点、確認できる実績、口コミの確認範囲、公式サイト CTA、掲載媒体、資料一覧、情報の限界を対象に合わせて書く。根拠がない欄は主張を作らず、確認できた範囲を明記する。
- `<title>`、`og:title`、Article JSON-LD `headline`、`h1` の**それぞれ**に「口コミ」「評判」「実績」を入れる。`description`、canonical、OG URL、構造化データの URL と日付もページ固有に更新する。記事内リンク、同社記事への相互リンク、公式サイト URL を確認する。
- トップ `site-v2/index.html` と一覧 `site-v2/articles.html` に記事を追加する。`scripts/build-public-v2.js` の `reportIds` に slug を追加する。`npm run build` により `dist/` と `sitemap.xml` が再生成される。表紙はユーザーが選んだ B 案を踏襲する。

2026年9月27日の一括追加分53記事には、公開元URL・公式案内・記事ごとの論点を `content/bulk-report-sources.json` と `content/bulk-report-angles.tsv` に記録しています。この53記事を訂正する場合は両ファイルと `scripts/generate-bulk-reports.py` の会社別説明を先に修正し、再生成してから検証してください。このスクリプトは当時の61記事の導線を再作成するため、後日追加された記事がある場合は安全のため停止します。通常の新規記事は上記の手順で作成します。

## 検証、公開、記録

```bash
node scripts/validate-public-v2.js
npm run build:branch-root
node scripts/stage-branch-root.js --check
python3 -m http.server 8080 --directory dist
```

ビルド後、ローカルのトップ、一覧、新規記事、同社記事との相互リンク、公式サイト CTA、PC とスマートフォンの表示、アニメーションの負担と縮小設定を確認します。検証スクリプトは構造上の漏れを検出するもので、ニュースの真偽や口コミの代表性は人が資料で確認します。公開前に `git diff` と `dist/` の対象を見直します。

公開がその依頼に含まれる場合は、現在のホスティングと権限を確認し、`npm run build:branch-root` の生成差分も含めて `main` へ反映します。ルートに旧サイトの補助ファイルが残っているため、新しい導線・サイトマップ以外の旧 URL は別途確認します。GitHub Actions の検証完了だけで終えず、`https://minnano-hyouban.com/` のトップ・一覧・新規記事・サイトマップを直接読み戻し、旧情報が残っていないか確認します。失敗や未確認はそのまま報告します。公開したコミット、記事 URL、確認時刻、差し戻し対象を作業記録に残します。認証情報は保存しません。
